# 個人品牌模組：口試問答備忘 (Defense Notes)

> 給團隊自己看的備忘。老師提醒：**網頁內容必須自己先弄懂**，不懂的名詞就從 `static/brand-knowledge.js` 刪掉，只留大家真的熟悉的。

## 1. 一句話說明「系統深度增加在哪」

不是只把資料來源換成 UCAN，而是三件事：

| 面向 | 以前 | 現在 |
|---|---|---|
| **精準度 (Precision)** | 自編 30 題，依 1 個 Holland 字母給 6 種固定建議 | 讀取 UCAN 三份官方報告（含 16 職涯類型、專業職能逐項 PR），**每個建議都標示來自哪個 UCAN 數字** |
| **落地性 (Actionability)** | 「學 Python」「建作品集」這類空泛建議 | 依**使用者選的目標職務**產生 30/60/90 天計畫，每個任務有「做什麼、交什麼成果、花多久、怎樣算完成」 |
| **可信度** | 內容由 AI 生成，無法解釋 | 規則與內容**人工整理**；報告附「為什麼是這個目標」與名詞小辭典 |

示範（對應老師舉的例子）：UCAN 顯示 **Holland A、就業途徑「視覺藝術」** → 推薦 **UI/UX 設計師** → 30 天學 Figma 並改版一個真實 App 畫面 → 60 天做可點擊原型並找 5 人測試 → 90 天寫成 Case Study 發在 Behance。同時因為「溝通表達 PR27、人際互動 PR14」偏低，每個階段自動多加一項補強任務；專業職能最低的項目（企劃、執行並管理藝術行政專案，PR41）也會排進第 60 天。

## 2. 資料流程

```
UCAN PDF (瀏覽器內解析，不上傳)
   → static/ucan-parser.js   解析成「UCAN 個人資料」(缺的報告不補預設值)
   → 使用者選擇未來目標 (系統推薦 3 個，或自選)
   → static/brand-engine.js  規則計算：契合度 / 30-60-90 / 社群策略 / 說明
   ← static/brand-knowledge.js  人工整理的職務劇本、人物、名詞
```

契合度 = 職業性格 35% + 職涯類型興趣 25% + 專業職能途徑 20% + 共通職能 20%（缺少的報告自動略過、權重重新分配）。**這是本專案依 Holland 人境適配理論設定的規則，不是 UCAN 官方公式**，口試時要主動講清楚。

## 3. 可能被問的問題

**Q1. 為什麼不用 AI 產生建議？**
A. 上次口試被質疑 AI 幻覺與缺乏學術依據。現在數據來自 UCAN，規則由我們整理且可說明；AI 不會即時生成任何建議或連結。

**Q2. 權重怎麼來的？有學術依據嗎？**
A. 方向依據 Holland 的人境適配理論（興趣類型與職業環境的一致性）以及 UCAN 本身把「興趣、共通職能、專業職能」並列的設計。權重數值是我們的設計決定，不是實證求得，所以報告上有標示並提供「為什麼」面板。

**Q3. 如果只有一份 UCAN 報告怎麼辦？**
A. 系統只使用有的報告，並明確提示缺哪些；不會補任何預設分數。（舊版曾經會補假分數，已移除。）

**Q3-1. 補強任務有官方依據嗎？**
A. 有。共通職能偏低時，報告會顯示 UCAN 官方「職場共通職能查詢」頁面對該能力的 主要指標、相關知識技能、相關活動（2026-11-03 擷取，附來源連結），我們的補強任務是依這些官方活動設計（例如 溝通表達 → 簡報、寫作、社團幹部）。

**Q4. 計畫怎麼做到「每個人不一樣」？**
A. 三個變數：①目標職務（13 種）②就業途徑與興趣（影響推薦順序）③偏低的共通職能與專業職能項目（自動加入補強任務）。測試案例見 `tests/brand/brand-engine.test.js`：同一個 Holland 字母、不同就業途徑，推薦會不同；同一目標、不同弱項，補強任務不同。

**Q5. 推薦的人物怎麼挑的？連結是真的嗎？**
A. 優先台灣經營者與社群，逐一打開確認過（`verifiedAt`），並用 `npm run check:links` 檢查。UI/UX 領域目前列的是台灣設計社群（UX 四神湯開放平台、一塊設計）與 Behance 搜尋入口；**建議團隊再親自挑 2–3 位台灣設計師的作品集補進去**（見下方待辦）。

**Q6. 名詞：Behance / Figma / Prototype / Case Study 是什麼？**
A. 全部寫在 `glossary`，報告最下方也有「名詞小辭典」。例：
- **Behance**：Adobe 旗下的創作者作品平台，設計師常在這裡發表完整專案。
- **Figma**：雲端介面設計工具，可多人同時編輯。
- **Prototype（原型）**：把畫面串成可點擊的模擬產品，開發前先測試流程。
- **Case Study**：把一個專案的問題、做法、結果、反思寫成故事，是設計師作品集的重點。

**Q7. UCAN 的資料隱私？**
A. PDF 只在使用者瀏覽器內解析，不上傳；登入後才儲存解析後的數字。專案內含真實姓名/學號的 PDF 已移出版本控制，測試改用匿名化的文字範例。

## 4. 目前限制與待辦（誠實面對）

- 規則權重與各系所對 Holland 類型的對應強度屬啟發式設定，未做實證驗證。
- 13 個職務之外的就業途徑，會以最接近的職務推薦。
- **需要團隊再確認內容的人物**（`needsTeamReview: true`）：`ggelis 部落格`（SA/BA）、`羽毛的電玩新手村`（遊戲）。`Harris 先生`、`羽毛的電玩新手村`、Behance 搜尋會擋機器人，需用瀏覽器手動確認。
- **建議補強**：UI/UX 與數位行銷各補 1–2 位台灣個人經營者（作品集 / 部落格 / IG）；補進 `creators` 時，請自己先看過內容並填 `verifiedAt`。
- UCAN 專業職能目前的就業途徑名稱，除了 PDF 實例（視覺藝術）外，其餘依既有程式碼使用的名稱；若 UCAN 官方名稱不同，以報告為準（解析器直接讀報告文字，不受影響）。

## 5. Demo 建議流程（3 分鐘）

1. 上傳 3 份 UCAN PDF → 展示解析出的數字（Holland、8 項共通職能、專業職能逐項）。
2. 進入「選擇未來目標」→ 說明為什麼推薦這 3 個（點出 UCAN 數字）。
3. 選 UI/UX → 展示 30/60/90、標著「來自 UCAN」的補強任務、勾選完成。
4. 切換成另一個目標（例如遊戲開發）→ 展示計畫完全不同。
5. 社群策略：點開人物連結，說明「看他怎麼分段，再模仿結構」；展開名詞小辭典。
6. 系所推薦頁：同一份 UCAN 資料，展示系所推薦的「依據」面板。
